# Feature Specification: 微信小程序样式适配

**Feature Branch**: `010-weapp-style-adapt`

**Created**: 2026-05-21

**Status**: Draft

**Input**: User description: "spec-009 让小程序编译跑通了但首页主体空白——根因是 H5 的 vh/vw 全屏布局在小程序失效（差异清单 R1）。本 spec 修这个布局问题，让小程序首页的搜索框/列表/筛选栏真正显示出来。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 小程序首页框架元素可见（Priority: P1）

用户在微信里打开小程序，希望看到一个**正常的首页**——搜索框、地图/列表模式切换、结果分类 tab、筛选栏、底部列表面板都该在它们该在的位置。而现在小程序首页除了顶部导航栏，主体一片空白。

**Why this priority**：P1，这是「小程序看起来像个能用的产品」的最低门槛。首页空白等于产品在小程序端根本没法用——spec-009 编译跑通了但用户看到的是白板。这个故事直接决定小程序端「有没有可用的界面」。

**Independent Test**：微信开发者工具里打开小程序首页，肉眼可见搜索框、模式切换按钮、筛选栏、底部列表/sheet —— 这些框架元素都渲染出来、位置合理、不塌陷重叠。

**Acceptance Scenarios**:

1. **Given** 小程序首页加载完成，**When** 用户查看首页，**Then** 能看到搜索框、地图/列表模式切换、结果分类 tab、筛选栏、底部列表/sheet 面板——框架元素可见且布局不塌陷
2. **Given** 首页有一块区域留给地图，**When** 首页渲染，**Then** 地图区域可以是空白/占位（地图本身的适配是后续 spec），但**不挤占或遮挡**其它框架元素
3. **Given** 用户在小程序里切换「地图/列表」模式，**When** 点击切换，**Then** 对应的视图区域正常显隐，布局不错乱

---

### User Story 2 - 求证进度存储在小程序端不报错（Priority: P2）

用户在小程序里浏览信源时，「求证进度」（看过哪些信源）应能被记住——这个功能原本用浏览器 `localStorage` 实现，小程序没有 `localStorage`。本故事确保它换成小程序兼容的存储方式后不报错、功能正常。

**Why this priority**：P2，比首页可见次要。求证进度是产品「信源求证」体验的一部分，但即使它暂时失效也不影响首页能不能看。归到本 spec 是因为它和 R1 同属「浏览器专属 API 在小程序不兼容」一类，顺带一起修。

**Independent Test**：小程序端浏览信源、触发求证进度打点，控制台无 `localStorage is not defined` 类报错；进度能被存取。

**Acceptance Scenarios**:

1. **Given** 小程序端用户浏览信源，**When** 触发求证进度打点，**Then** 控制台无存储相关报错
2. **Given** 用户看过某信源后重新进入，**When** 页面读取求证进度，**Then** 能正确读回之前的进度

---

### User Story 3 - H5 端零回归（Priority: P1）

开发者希望本 spec 所有为小程序做的样式/存储改动，**不破坏 H5 端**——H5 首页的布局、视觉、求证进度功能与改动前完全一致。

**Why this priority**：P1，H5 是已上线可用的形态。为小程序改样式时如果把 H5 改坏了，就是「修一个端、坏一个端」的负和操作。零回归是硬约束。

**Independent Test**：`build:h5` 成功；H5 首页布局与改动前肉眼一致；H5 求证进度功能正常。

**Acceptance Scenarios**:

1. **Given** 本 spec 完成，**When** 跑 H5 构建并打开首页，**Then** 首页布局/视觉与改动前一致，无错位、无塌陷
2. **Given** H5 端求证进度功能，**When** 改动后使用，**Then** 与改动前行为一致

---

### Edge Cases

- 小程序不同机型屏幕高度不同：全屏布局须能自适应各机型高度，不能写死像素高度
- 小程序顶部导航栏 / 状态栏占位：全屏内容区高度须扣除系统占位，不能与导航栏重叠
- `min()` 等较新 CSS 函数小程序老基础库不支持：用兼容写法替代
- 改动后 H5 与小程序对同一份 CSS 的解释差异：用平台条件（`TARO_ENV`）或双端都成立的写法，避免「改好一端坏另一端」
- 求证进度存储：小程序端首次无历史数据时读取应返回空而非报错

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 让小程序首页的框架元素（搜索框、地图/列表模式切换、结果分类 tab、筛选栏、底部列表/sheet 面板）在微信小程序端正常渲染、位置合理、不塌陷不重叠
- **FR-002**: 系统 MUST 把首页全屏布局所依赖的视口单位（`vh`/`vw`）改为微信小程序兼容的方式——全屏高度用小程序可正确计算的写法（如百分比高度 + 根节点链，或运行时取屏幕高度）
- **FR-003**: 系统 MUST 把小程序不兼容的 CSS 写法（如 `inset` 简写、`min()` 等函数）替换为小程序可解释的等价写法
- **FR-004**: 系统 MUST 让全屏内容区高度自适应不同机型，并正确扣除小程序系统导航栏/状态栏占位，不与之重叠
- **FR-005**: 系统 MUST 把求证进度的浏览器 `localStorage` 存储替换为小程序兼容的存储方式，H5 端仍可用同一套逻辑
- **FR-006**: 系统 MUST 保证 H5 端零回归——首页布局、视觉、求证进度功能与改动前一致；`build:h5` 正常
- **FR-007**: 系统 MUST NOT 修复地图本身（地图区域空白/占位可接受，归地图适配 spec）、信源外链、后端 API 网络层、AI 内容标注
- **FR-008**: 系统 MUST NOT 改动业务逻辑与后端代码（本 spec 仅前端样式 + 存储 API 适配）

### Key Entities

- **首页布局结构**：全屏容器 + 地图区 + 浮层（搜索框/模式切换/分类 tab/筛选栏）+ 底部列表/sheet —— 本 spec 让这套结构在小程序端成立
- **求证进度存储**：记录用户看过的信源；存储介质从 `localStorage` 抽象为双端兼容的存储 API

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 微信开发者工具里小程序首页，框架元素（搜索框/模式切换/筛选栏/底部列表）全部可见——人工核验，可见率 100%（不含地图本身）
- **SC-002**: 小程序首页布局在至少 2 种机型模拟器（如 iPhone 12/13 + 一款小屏机型）下不塌陷、不错位、不与导航栏重叠
- **SC-003**: 小程序端控制台无 `localStorage`/视口单位 相关报错
- **SC-004**: H5 端首页布局与改动前肉眼一致——人工对比无可察觉差异；`build:h5` 成功
- **SC-005**: 地图区域在小程序端为空白/占位，但不遮挡、不挤占其它框架元素

## Assumptions

- spec-009 已完成：小程序能编译、能在微信开发者工具启动，差异清单已产出
- 本 spec 处理差异清单的 R1（vh/vw 全屏布局）+ R5（localStorage）两项
- 地图（R2）、信源外链（R3）、后端网络层（R4）、AI 标注（R6）不在本 spec，各有独立 spec
- 前端是 Taro 4 + React 18，样式改动通过 Taro 的多端编译同时作用于 H5 与小程序；平台差异处用 `TARO_ENV` 条件或双端兼容写法处理
- 验证靠：`build:weapp` + 微信开发者工具人工核验首页 / `build:h5` + H5 人工核验不回归——本 spec 无单元测试可加（纯样式）
- 「H5 视觉与改动前一致」以人工肉眼对比为准，不引入像素级回归测试工具
