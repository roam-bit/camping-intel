# Feature Specification: 修复微信小程序端点位数据加载不出来

**Feature Branch**: `013-fix-weapp-data-load`

**Created**: 2026-05-22

**Status**: Draft

**Input**: User description: "微信小程序端启动后地图无点位 marker、Network 无后端请求、Console 报 Error: timeout。已查证根因链：loadPlaces 只在定位 ok 时触发；小程序定位因 app 未声明定位权限必失败 → loadPlaces 永不触发 → 点位永不加载。本 spec 让小程序端不论定位成败都能加载并显示点位数据，并消除 Error: timeout。仅前端，H5 零回归。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 小程序端能看到点位数据（Priority: P1）

用户在微信小程序里打开首页，希望地图上能看到露营/驻车点位、底部列表里有内容——而现在小程序端地图永远空空如也、底部「来源点位 0」，因为点位数据根本没被加载。这等于产品在小程序端「打开就是个空壳」。

**Why this priority**：P1，这是「小程序端是不是一个能用的产品」的根本。没有点位数据，地图组件（spec-012）做得再好也只是一张没有内容的底图。

**Independent Test**：微信开发者工具打开小程序首页，不做任何操作，地图上出现点位 marker、底部列表有点位条目。

**Acceptance Scenarios**:

1. **Given** 用户打开小程序首页，**When** 页面加载完成，**Then** 点位数据被加载，地图上出现点位 marker、底部列表有点位
2. **Given** 小程序向后端取点位数据，**When** 请求发出，**Then** 能在网络层观察到对后端点位接口的真实请求（而非「一个请求都没发」）

---

### User Story 2 - 定位失败/未授权时仍能看到点位（Priority: P1）

用户即使**拒绝定位授权**、或定位失败，也希望仍能看到点位——用一个默认中心（杭州）兜底，而不是「因为没定位就整个空白」。当前定位一失败，点位加载就被卡死。

**Why this priority**：P1，定位失败是极常见场景（用户拒绝授权、设备定位不可用）。「没定位 = 没内容」是不可接受的脆弱设计。这条恰恰是当前小程序空白的直接原因（小程序定位必失败）。

**Independent Test**：在定位被拒绝/失败的情况下，小程序首页仍能加载并显示点位（基于默认中心）。

**Acceptance Scenarios**:

1. **Given** 用户拒绝定位授权，**When** 首页加载，**Then** 用默认中心（杭州）加载并显示点位，不空白
2. **Given** 定位获取失败（设备不支持/超时等），**When** 首页加载，**Then** 同样用默认中心加载并显示点位
3. **Given** 用户授权且定位成功，**When** 首页加载，**Then** 用真实定位加载周边点位（行为不退化）

---

### User Story 3 - 小程序可正常获取定位授权（Priority: P2）

用户授权位置后，希望小程序能拿到真实定位、显示「我附近」的点位。当前小程序的定位调用因缺少权限声明而必然失败，用户连授权弹窗都见不到。

**Why this priority**：P2。比 US1/US2 次要——US2 的兜底已保证「没定位也能用」；本故事是让「定位成功」这条更优路径在小程序端真正可用。

**Independent Test**：微信开发者工具中小程序首次进入会弹出位置授权请求；授权后地图能居中到（模拟的）真实位置。

**Acceptance Scenarios**:

1. **Given** 小程序首次需要定位，**When** 触发定位，**Then** 正常弹出微信位置授权请求（而非直接失败、无弹窗）
2. **Given** 用户在授权弹窗中同意，**When** 定位返回，**Then** 拿到真实坐标并据此加载周边点位

---

### User Story 4 - 启动无报错（Priority: P2）

开发者希望小程序启动时控制台干净——当前启动会冒出一条未被捕获的 `Error: timeout` 红色报错。即使它不一定阻断功能，未捕获的报错也是隐患、且干扰排查。

**Why this priority**：P2。它是否直接阻断数据加载尚待查证；但「启动即报错」必须消除——要么修掉根源，要么妥善捕获处理。

**Independent Test**：微信开发者工具小程序启动，Console 无未被捕获的 `Error: timeout`。

**Acceptance Scenarios**:

1. **Given** 小程序启动，**When** 查看 Console，**Then** 无未被捕获的 `Error: timeout`（错误被消除，或被妥善捕获并降级处理）

---

### User Story 5 - H5 端零回归（Priority: P1）

开发者希望本 spec 的改动**不破坏 H5 端**：H5 定位成功时的行为与现在完全一致。同时——H5 端其实也存在「定位失败就不加载点位」的同款隐患，本 spec 的兜底修复应让 H5 在定位失败时也能用默认中心加载点位（属修复、非回归）。

**Why this priority**：P1，H5 是已上线形态。改动不能让 H5 定位成功路径退化。

**Independent Test**：`build:h5` 成功；H5 定位成功时点位加载与改动前一致；H5 定位失败时也能用默认中心显示点位。

**Acceptance Scenarios**:

1. **Given** H5 端定位成功，**When** 首页加载，**Then** 点位加载行为与改动前完全一致
2. **Given** H5 端定位失败/被拒，**When** 首页加载，**Then** 用默认中心加载并显示点位（不再空白）

---

### Edge Cases

- 定位「请求中」（pending）迟迟不返回：点位加载不应无限期等定位——应有合理的兜底触发，不让用户干等
- 用户先拒绝、之后在系统设置里又授权：行为应可预期，不卡死
- 默认中心（杭州）附近恰好无点位：地图与列表正常显示「该区域暂无点位」，不报错、不空白卡死
- 后端不可达 / 点位请求失败：应有用户可见的失败提示，不是静默空白
- H5 与小程序对「定位失败」的错误形态不同（浏览器 geolocation vs 微信 API）：两端都要能识别为「失败」并走兜底

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在小程序端首页加载时获取并显示点位数据，使地图出现 marker、列表有内容
- **FR-002**: 点位数据的加载 MUST NOT 被「定位是否成功」单一门槛卡死——定位失败/未授权时，系统 MUST 用默认中心（杭州）加载点位
- **FR-003**: 定位成功时，系统 MUST 用真实定位加载周边点位（保持现有更优行为）
- **FR-004**: 小程序端 MUST 声明定位所需的权限，使位置获取能正常发起（弹出授权请求），而非未声明导致必然失败
- **FR-005**: 系统 MUST 消除小程序启动时未被捕获的 `Error: timeout` 报错——根因查清后修掉根源，或将该错误妥善捕获并降级，不留未捕获报错
- **FR-006**: 点位请求失败时，系统 MUST 给用户可见的提示，不静默空白
- **FR-007**: 系统 MUST 保持 H5 端零回归——定位成功时点位加载行为与改动前一致；并让 H5 在定位失败时也能用默认中心加载点位
- **FR-008**: 系统 MUST NOT 改动后端、AI 搜索的后端出网问题、spec-012 的地图组件

### Key Entities

- **定位状态**：表示用户位置获取的结果——成功/拒绝/失败/进行中；它**不应**成为「能否加载点位」的唯一开关
- **加载中心坐标**：决定向后端请求哪片区域点位的中心点；定位成功用真实坐标，否则用默认中心（杭州）
- **点位数据**：从后端取回的露营/驻车点位集合，渲染为地图 marker 与列表

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 微信开发者工具小程序首页加载后，地图出现点位 marker、底部列表有点位条目——人工核验，非空
- **SC-002**: 小程序启动后，网络层能观察到对后端点位接口的真实请求（请求数 ≥ 1，不再是 0）
- **SC-003**: 定位「授权成功」与「拒绝/失败」两种情况下，小程序首页都能显示点位——两种场景人工核验均通过
- **SC-004**: 微信开发者工具小程序启动，Console 无未被捕获的 `Error: timeout`
- **SC-005**: 小程序首次定位时能正常弹出微信位置授权请求
- **SC-006**: H5 端定位成功时点位加载与改动前肉眼一致；定位失败时 H5 也能显示点位；`build:h5` 成功

## Assumptions

- spec-009/010/011/012 已完成：小程序能编译、首页框架与地图可见、网络层就绪
- 后端正常：已用 curl 验证 `/api/v1/places` 秒回且有数据，本 spec 不碰后端
- 本 spec 仅前端改动，涉及 app 配置（定位权限声明）、首页加载逻辑、定位 hook
- 「默认中心」沿用代码中已有的杭州默认坐标（`HANGZHOU_FALLBACK`）
- `Error: timeout` 的确切根因尚未证实——留待 plan/research 阶段查清；本 spec 只规定「结果上不能有未捕获报错」，不预设修法
- 验证靠：`build:weapp` + 微信开发者工具人工核验（含定位授权/拒绝两种场景）/ `build:h5` + H5 人工核验；本 spec 无前端单测设施
- 微信开发者工具中验证后端请求仍依赖「不校验合法域名」+ 本地后端可达
