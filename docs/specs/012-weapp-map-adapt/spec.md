# Feature Specification: 微信小程序地图层适配

**Feature Branch**: `012-weapp-map-adapt`

**Created**: 2026-05-21

**Status**: Draft

**Input**: User description: "微信小程序地图层适配（R2，用微信原生 <map> 组件）。当前 MapCanvas 用高德 JS API，被 TARO_ENV 守卫挡住——小程序端地图区是空白。微信小程序不允许加载高德 JS SDK，要显示地图只能用地图组件。已定方案：用微信原生 <map> 组件（腾讯底图），不用高德小程序插件。本 spec 让小程序地图能显示、有点位 marker、点 marker 开详情、定位/搜索居中，H5 零回归。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 小程序首页地图底图可见（Priority: P1）

用户在微信里打开小程序首页，希望看到一张**真实的、可拖动可缩放的地图**——而现在小程序端地图区是一片空白。地图是这个产品的主界面，没有地图等于产品在小程序端只剩半张脸。

**Why this priority**：P1，这是「小程序端有没有地图」的最低门槛。差异清单 R2 的核心就是它。地图空白时，后面的 marker、居中都无从谈起。

**Independent Test**：微信开发者工具打开小程序首页，地图区显示一张真实地图，能用手指拖动、双指缩放。

**Acceptance Scenarios**:

1. **Given** 小程序首页加载完成，**When** 用户查看地图区，**Then** 显示一张真实可交互的地图（可拖动、可缩放），而非空白
2. **Given** 小程序地图已显示，**When** 用户拖动或缩放地图，**Then** 地图正常响应

---

### User Story 2 - 点位在小程序地图上可见可点开（Priority: P1）

用户在小程序地图上希望看到搜索/底库的点位标记（marker），并能点击某个 marker 打开它的详情——这是「在地图上发现露营点」的核心动作。

**Why this priority**：P1，地图的价值在于「图上能看到点、能点开」。只有底图没有点位，地图只是个装饰。

**Independent Test**：小程序端有点位数据时，地图上出现对应数量的 marker；点击任一 marker 能打开该点位的详情。

**Acceptance Scenarios**:

1. **Given** 小程序端有 N 个点位数据，**When** 地图渲染，**Then** 地图上出现 N 个点位 marker，且每个 marker 能让用户看出该点的信源数
2. **Given** 小程序地图上有 marker，**When** 用户点击某个 marker，**Then** 打开该点位的详情，与 H5 端点击 marker 的行为一致
3. **Given** 当前区域无点位数据，**When** 地图渲染，**Then** 地图正常显示（无 marker 可接受），不报错、不空白

---

### User Story 3 - 地图随定位/搜索自动居中（Priority: P1）

用户定位成功后，希望地图自动飞到自己附近；用户搜索某个地名后，希望地图自动飞到该地区或搜索结果点位的范围——而不是一直停在默认位置让用户自己找。

**Why this priority**：P1，「搜了『漠河露营』地图却停在杭州」会让用户以为搜索没生效。居中是搜索体验成立的一部分。

**Independent Test**：小程序端定位成功后地图中心在用户位置附近；搜索某地名后地图视野移动到对应区域/点位范围。

**Acceptance Scenarios**:

1. **Given** 小程序端用户定位成功，**When** 地图初始化或定位返回，**Then** 地图中心居中到用户位置、缩放级别合理
2. **Given** 用户搜索某地名且有结果点位，**When** 结果返回，**Then** 地图视野调整到能容纳这些点位的范围
3. **Given** 用户搜索某地名但无结构化点位，**When** 结果返回，**Then** 地图视野移动到该地名对应的中心区域

---

### User Story 4 - H5 端地图零回归（Priority: P1）

开发者希望本 spec 为小程序加地图的所有改动，**不破坏 H5 端**——H5 的高德地图、点位 marker、缩放控件、自动 fitView、定位居中，与改动前完全一致。

**Why this priority**：P1，H5 是已上线可用形态。为小程序加地图时把 H5 地图改坏，是「修一端坏一端」的负和操作。

**Independent Test**：`build:h5` 成功；H5 首页高德地图显示、marker、控件、搜索后 fitView、定位居中 与改动前一致。

**Acceptance Scenarios**:

1. **Given** 本 spec 完成，**When** 跑 H5 构建并打开首页，**Then** 高德地图、点位 marker、缩放控件 与改动前一致
2. **Given** H5 端搜索与定位，**When** 改动后使用，**Then** 地图 fitView、定位居中 行为与改动前一致

---

### User Story 5 - 小程序端「一键导航」可用（Priority: P2）

用户在小程序点位详情里点「一键导航」，希望能唤起导航——而当前导航靠浏览器 `window.open` 打开高德网页 URL，小程序不支持，点了无反应。

**Why this priority**：P2，比「地图能显示」次要。导航是点位详情里的动作，即使暂时失效也不影响地图主体可用。归本 spec 是因为它和地图同属「高德浏览器能力在小程序失效」一类，顺带一起修。

**Independent Test**：小程序端点位详情点「一键导航」，能唤起小程序可用的导航方式（如系统地图导航）。

**Acceptance Scenarios**:

1. **Given** 小程序端点位详情，**When** 用户点「一键导航」，**Then** 唤起小程序可用的导航（如打开系统地图并定位到该点），不再无反应

---

### Edge Cases

- 小程序原生地图组件层级：地图组件**不能遮挡**首页其它浮层元素（搜索框、地图/列表模式切换、结果分类 tab、筛选栏、底部列表/sheet 面板）——须确保浮层在地图之上可见可点
- 当前区域 0 个点位：地图须正常显示一个合理默认视野（用户定位或默认城市），不空白、不报错
- 原生地图 marker 自定义能力有限（不能放任意 HTML）：信源数等信息须用地图组件支持的方式（图标 + callout/气泡/label）呈现，不能因此丢失「能看出信源数」这一信息
- 定位权限被用户拒绝：地图应回退到默认城市视野，不报错卡死
- 点位坐标异常（缺失/越界）：单个坏点位不应导致整张地图或其它 marker 渲染失败
- H5 与小程序对同一 MapCanvas 组件的双端编译：平台分支须互不干扰，改一端不影响另一端

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在微信小程序端首页地图区显示一张真实、可拖动、可缩放的地图，替代当前的空白占位
- **FR-002**: 系统 MUST 在小程序地图上为每个点位（places 数据）渲染一个 marker
- **FR-003**: 小程序地图的 marker MUST 用地图组件支持的方式呈现，并让用户能看出该点位的信源数；不依赖 H5 端的自定义 HTML marker
- **FR-004**: 用户点击小程序地图上的 marker MUST 触发「打开该点位详情」，行为与 H5 端点击 marker 一致
- **FR-005**: 小程序地图 MUST 支持自动居中——定位成功时居中到用户位置；搜索有结果时调整视野到点位范围；搜索无结构化点位时移动到搜索地名的中心区域
- **FR-006**: 小程序地图 MUST NOT 遮挡首页其它浮层元素（搜索框、模式切换、分类 tab、筛选栏、底部列表/sheet）——这些浮层须在地图之上可见可交互
- **FR-007**: 系统 MUST 保持 H5 端地图零回归——高德地图、自定义 marker、缩放控件、搜索后 fitView、定位居中 与改动前一致；`build:h5` 正常
- **FR-008**: 系统 MUST 让小程序端「一键导航」可用——点击触发小程序可用的导航方式，不依赖 H5 的 `window.open`
- **FR-009**: 系统 MUST 在当前区域无点位、定位被拒、单个点位坐标异常等情况下保持地图可用、不崩溃
- **FR-010**: 系统 MUST NOT 改动后端、信源「查看原文」外链（R3）、AI 生成内容标注（R6）

### Key Entities

- **地图视图**：小程序端首页的地图，含底图、视野中心、缩放级别；可被定位/搜索驱动居中
- **点位 marker**：一个点位在地图上的标记，含位置坐标、图标、信源数标识；可被点击
- **居中策略**：决定地图视野的三种触发源——用户定位、搜索中心、点位范围

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 微信开发者工具小程序首页，地图区显示可交互地图（可拖动、可缩放）——人工核验，可见
- **SC-002**: 小程序端有 N 个点位时，地图上 marker 数 = N，且每个 marker 可看出信源数
- **SC-003**: 点击小程序地图上任一 marker，能打开对应点位详情——人工核验
- **SC-004**: 定位成功 + 搜索某地名 两个场景下，小程序地图视野居中正确——人工核验至少这 2 个场景
- **SC-005**: 小程序首页地图不遮挡搜索框、模式切换、分类 tab、筛选栏、底部列表面板——这些浮层全部可见可点
- **SC-006**: H5 端地图与改动前肉眼一致——地图、marker、控件、fitView、定位居中 正常；`build:h5` 成功
- **SC-007**: 小程序端点位详情点「一键导航」能唤起导航——人工核验

## Assumptions

- spec-009/010/011 已完成：小程序能编译、首页框架可见、网络层就绪
- 本 spec 处理差异清单的 R2（地图层），仅前端改动
- 地图方案已定：微信原生 `<map>` 组件（Taro `<Map>`，腾讯地图底图），不用高德小程序插件——用户已拍板
- 坐标沿用现有 `wgs84ToGcj02` 转换：高德与腾讯均用 GCJ-02 火星坐标，转换通用，无需为小程序改坐标逻辑
- marker 聚合（cluster）：H5 端有高德 MarkerCluster；小程序端本 spec 点位量级（搜索结果约十余个）下聚合非必需，不强制实现——视图清晰即可，聚合可作后续优化
- 底图视觉差异（小程序腾讯底图 vs H5 高德底图）已被用户接受，不在本 spec 追求两端底图一致
- 验证靠：`build:weapp` + 微信开发者工具人工核验 / `build:h5` + H5 人工核验零回归；本 spec 无前端单测设施（纯 UI/地图）
- R4（网络层）已就绪，但小程序连后端取真实点位数据仍依赖真实备案域名——本 spec 验证 marker 时可用本地后端数据或微信开发者工具「不校验合法域名」环境
