# Feature Specification: 修复微信小程序真机地图初始视野不居中

**Feature Branch**: `016-fix-weapp-map-view`

**Created**: 2026-05-23

**Status**: Draft

**Input**: User description: "修复微信小程序真机上『地图初始视野不居中到用户定位』的 bug。真机调试中，定位成功后定位蓝点（系统原生 showLocation）位置正确，但地图画面没有居中到该位置、卡在别处（疑似硬编码的杭州城区范围）。微信开发者工具模拟器上不明显（spec-014 在模拟器验过、误判为已修），真机才暴露。根因高度怀疑是 `MapCanvas.weapp.tsx` 传给原生 `<map>` 的 `include-points`（spec-014 为防崩溃加的固定常量）锁死了视野，使受控经纬度失效。修复须保留 spec-014 的崩溃修复。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 初始定位后地图居中到用户位置（Priority: P1）

用户在真机上打开小程序，定位成功后，希望地图画面**居中到自己所在的位置**，能立刻看到「我在哪、附近是什么」。当前真机上的实际表现是：定位蓝点画在了正确位置，但地图画面（视野中心 + 缩放）停在别处——用户得手动拖动地图才能找到自己。

**Why this priority**：P1，这是本次要修的核心 bug。地图产品打开第一眼不在用户位置上，等于产品的第一印象就是坏的。

**Independent Test**：真机调试打开小程序，定位成功后，不做任何操作——地图画面中心就在用户实际位置附近，定位蓝点居中可见。

**Acceptance Scenarios**:

1. **Given** 真机上小程序首次打开且定位成功，**When** 用户查看地图，**Then** 地图视野中心居中到用户定位坐标、缩放级别能看清周边，定位蓝点在画面中心附近
2. **Given** 真机定位成功，**When** 用户未做任何拖动，**Then** 不存在「蓝点在一处、地图画面在另一处」的错位

---

### User Story 2 - 视野随定位/搜索更新而跟随（Priority: P1）

定位坐标更新（如初始用兜底坐标、随后拿到真实 GPS）、或搜索返回了结果（点位 / 搜索地名中心）后，用户希望地图视野**跟着移动**到对应的位置或范围，而不是停在旧视野。

**Why this priority**：P1，与 US1 同源——视野控制机制如果坏了，初始居中和后续跟随会一起坏。修复必须让视野能被「正确目标」可靠驱动。

**Independent Test**：真机上，定位由兜底坐标更新为真实坐标后地图跟着移动；搜索出点位后地图移动到点位范围。

**Acceptance Scenarios**:

1. **Given** 真机定位坐标发生更新，**When** 新坐标返回，**Then** 地图视野跟随移动到新坐标
2. **Given** 真机搜索返回结构化点位，**When** 结果渲染，**Then** 地图视野调整到能容纳这些点位的范围
3. **Given** 真机搜索返回地名但无结构化点位，**When** 结果返回，**Then** 地图视野移动到该地名中心区域

---

### User Story 3 - 修复视野不重新引入 `<map>` 崩溃（Priority: P1）

开发者希望本次修视野的改动，**不破坏 spec-014 的崩溃修复**——微信小程序原生 `<map>` 不得因 include-points 退回空数组（或其它原因）重新触发 spec-014 查明的渲染崩溃。

**Why this priority**：P1，spec-014 的崩溃是阻断级问题。修视野时把崩溃修复弄丢，是「修一个坏一个」的负和操作。

**Independent Test**：真机调试，地图加载与交互全程无 `<map>` 渲染崩溃（spec-014 的 `Cannot read property 'lat'` 不复现）。

**Acceptance Scenarios**:

1. **Given** 本次修复完成，**When** 真机加载地图、定位、搜索、拖动，**Then** 全程无 `<map>` 渲染崩溃

---

### Edge Cases

- **定位失败 / 被拒**：用户坐标退化为兜底默认坐标（杭州）——视野应居中到该默认坐标，不卡在无关位置、不崩溃
- **定位较慢**：`getLocation` 在超时（约 8 秒）前未返回——视野先用兜底坐标、真实坐标返回后跟上
- **搜索结果 0 / 1 / 多个点位**：视野各自合理（沿用 spec-012/014 的优先级：多点位包围盒 > 单点位 > 搜索中心 > 用户定位）
- **崩溃护栏不可丢**：include-points 不得为空数组——这是 spec-014 崩溃的直接触发条件
- **真机 ≠ 模拟器**：原生 `<map>` 视野行为在微信开发者工具模拟器与真机上不一致——任何「修好了」的判断只以真机为准

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 真机微信小程序上，初始定位成功后，地图视野 MUST 居中到用户定位坐标，且缩放级别能看清周边
- **FR-002**: 当用户定位坐标更新、或搜索返回结果（结构化点位 / 搜索地名中心）时，地图视野 MUST 跟随更新到对应目标，不停留在旧视野
- **FR-003**: 系统 MUST 保留 spec-014 的崩溃修复——原生 `<map>` 的 include-points 不得退回空数组，本次修复不得重新触发 spec-014 查明的 `<map>` 渲染崩溃
- **FR-004**: 定位失败 / 被拒时，地图视野 MUST 居中到兜底默认坐标，不卡在无关位置、不崩溃
- **FR-005**: 本次修复 MUST 仅改动微信小程序端地图视野控制逻辑；H5 端地图（高德 JS API）MUST 零回归
- **FR-006**: 视野优先级 MUST 沿用既有语义——多点位包围盒 > 单点位 > 搜索中心 > 用户定位

### Key Entities

- **地图视野**：微信小程序地图当前的可视范围——含中心坐标与缩放级别
- **视野目标**：决定视野该对准哪里的来源——用户定位坐标 / 搜索地名中心 / 点位集合包围盒
- **崩溃护栏**：为防 spec-014 空数组崩溃而存在的 include-points 非空保障——修复后必须仍然成立

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 真机调试——打开小程序、定位成功后，地图画面居中到用户位置（人工核验，真机）
- **SC-002**: 真机——定位坐标更新后、搜索后，视野跟随到对应位置/范围（人工核验至少这 2 个场景）
- **SC-003**: 真机——定位蓝点与地图画面中心一致，不再出现「蓝点一处、画面一处」的错位
- **SC-004**: 真机——地图加载、定位、搜索、拖动全程无 `<map>` 渲染崩溃
- **SC-005**: H5 端地图与改动前肉眼一致（零回归）；`build:h5` 与 `build:weapp` 均构建成功

## Assumptions

- spec-014 已合并 main；`MapCanvas.weapp.tsx` 现有的「受控 longitude/latitude/scale + include-points 固定崩溃护栏」是本次修复的起点
- **根因高度怀疑是 include-points 锁死视野、受控经纬度被压制——但此为推测**。plan / 实现阶段 MUST 在真机上实测核实根因后再确定修复方案，不得直接把推测当定论动手（沿用错题本对 spec-014「凭假设改 `<map>` 反复翻车」的教训）
- **验收以真机为准**：原生 `<map>` 视野行为在微信开发者工具模拟器与真机上不一致，模拟器表现不作为「修好了」的通过依据
- 本次为纯前端微信小程序端改动，不涉及后端、不涉及 H5 端地图代码
- 不含「真机搜索连不上后端（API 指向 127.0.0.1）」那个独立的基础设施问题——那是后端部署/网络问题，不在本规格范围
- 验证手段：真机调试人工核验 + `build:h5`/`build:weapp` 构建；前端无自动化测试设施

## 关键约束（过程要求，非系统行为）

本 bug 涉及微信原生 `<map>` 的视野控制——spec-014 已在此反复失败多轮（详见错题本）。本规格对实现过程作硬性约束：

- 修复方案确定前，MUST 先在真机上实测核实根因（include-points 是否真的锁死视野、受控经纬度在真机上到底起不起作用）
- 「修好了」的判断 MUST 以真机调试实测为准；微信开发者工具模拟器的表现仅供参考、不作通过依据
- 修复 / 验证大概率需要「改一版 → 用户真机测 → 再改」的多轮迭代——开发者无法自行真机测试，此循环须由用户配合
