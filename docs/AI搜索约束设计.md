# AI搜索约束与提示词说明 P0.3

本文档整理当前产品中对 AI 搜索、AI 分析、结构化抽取、入图展示施加的全部主要约束，供产品侧查看和后续修改。

更新时间：2026-05-13

## P0.3 关键变化

P0.3 的策略已经从“实时 AI 搜索直接决定地图上有哪些点”改为“双层架构”：

1. POI 底库先铺地图，来源包括 OSM 冷启动、公开资料整理、后续用户提交和审核后的 AI 候选。
2. AI 负责联网回答、来源核验、设施/风险摘要和候选点增强。
3. AI 搜索结果必须通过分析评估后才能进入正式 `places` 库；未通过的结果进入 `pending_review` 或 `unmapped_candidates`。
4. 地图主服务改为高德地图；前端正式技术栈改为 Taro，H5 先行。
5. 正式 API 路径统一为 `/api/v1/...`，核心入口是 `/api/v1/places` 和 `/api/v1/ai/search`。
6. 默认候选数量从 6 提升到 12；数量提升主要依赖 POI 底库，不再要求 Seed 单次搜索承担全部点位发现。

## 一、为什么当前只能展示少量点位

之前产品展示点位少，不主要是 Seed 模型能力不足，而是 P0.2 链路选择了“先保证来源可信和坐标可信，再展示少量候选点”的策略。它和窝友自驾的点位机制不同。

窝友自驾更像是一个已经积累过的 POI/UGC 点位库。它可以先把大量历史用户提交点位铺在地图上，再用评分、厕所、水、电等标签过滤。即使没有新的搜索行为，地图上也天然有很多点。

P0.3 之后，实时 AI 搜索不再是唯一点位来源。用户打开地图时，先展示 `places` 底库；用户搜索时，Seed 联网回答会生成新线索，并把通过评估的候选沉淀进底库。

当前导致点位少的主要约束如下：

1. P0.2 前端请求写死 `limit=6`，后端提示词也要求“尽量列出 6 个以内”。P0.3 已改为默认 `limit=12`。
2. AI 搜索仍只使用 Ark Responses API + `web_search`，但地图数量由 `places` POI 底库提供兜底。
3. Seed Web Search 返回的是带引用的联网回答，不是无限量搜索结果列表。实测一条查询常见只返回 3-5 个可追溯来源。
4. 第二段结构化抽取要求每个点位必须绑定真实 `source_ids`，没有来源 ID 的点直接丢弃。
5. 系统禁止编造点名、坐标、设施、开放状态。这个约束提升可信度，但会减少数量。
6. 地图入图要求有明确坐标，或高德/Nominatim 能把具体地点解析成可信坐标。只有城市、区县、文章标题、泛化描述时不入图。
7. 坐标如果偏离查询地点太远，会被转成未入图线索。
8. 前端如果选择了信源时间范围，日期未知或超过时间范围的点位会被隐藏。
9. 默认勾选了“可过夜”，会过滤掉明确不可过夜的点。

结论：如果目标是像窝友自驾一样“地图上天然很多点”，只靠实时 AI 联网搜索不够。更合理的产品链路应该是：

- 先用地图 POI / 用户提交 / 历史缓存 / 公开数据生成大量候选池；
- 再让 AI 对候选点做联网核验、标签补全、风险摘要和来源归因；
- 地图上展示“候选点很多”，详情里区分“已核验 / 待核验 / 来源不足”。

## 二、当前 AI 链路总览

当前 `/api/v1/ai/search` 的主要流程：

1. Taro 前端搜索框调用后端：`POST /api/v1/ai/search`，默认 `limit=12`。
2. 后端第一段调用 Seed Responses API + `web_search`，生成中文联网回答。
3. 后端第二段调用 Seed，对第一段回答做 JSON 结构化抽取。
4. 后端用高德地理编码把具体地点转成坐标。
5. 后端过滤泛化标题、无来源点、无可信坐标点、坐标偏离点。
6. 前端再按设施、过夜、费用、信源时间范围筛选展示。

## 三、前端传给后端的数量约束

代码位置：`frontend/src/pages/index/index.tsx`

当前请求：

```js
aiSearch(query, 12, radiusKm)
```

含义：

- 每次 AI 搜索默认请求 12 个候选点。
- 后端会把这个 `limit` 传入 Seed 提示词。
- 因此 AI 即使能找到更多，也会被提示词限制在 6 个以内。

可调整方向：

- P0.3 稳定后可按性能改为 `limit=20`。
- 如果追求地图点位数量，应拆成两个参数：
  - `answerLimit`：回答里重点解释的点位数，例如 6 个；
  - `candidateLimit`：结构化抽取和地图展示的候选数，例如 20-50 个。

## 四、第一段 Seed 联网回答提示词

代码位置：`backend/app/services/ai_service.py` 的 `call_seed_web_answer`

当前提示词：

```text
你是自驾游、穷游、露营、床车和房车场景的垂类AI助手。
请必须联网搜索公开网页，优先选择最近、可追溯、和用户地点强相关的信息源。
回答要像面向真实出行用户的简明建议，不要输出JSON。

用户问题：{query}

请尽可能多列出候选露营/驻车线索，优先列出 {limit} 个。每个候选点必须包含：
地点名、城市/区县或地址线索、费用线索、是否提到可露营/过夜、停车、厕所、水源、信息日期、来源链接。
如果来源没有提到某字段，明确写“来源未提到/未核验”。
不要把搜索页、地图入口页、政策汇总页当作事实来源；不要编造坐标、设施或开放状态。
涉及安全、合法、过夜、明火时只陈述来源事实，不下最终保证。
```

这里对 AI 的主要约束：

- 必须联网搜索公开网页。
- 优先选择最近、可追溯、地点强相关来源。
- 输出中文自然语言回答，不输出 JSON。
- 候选点数量目标为 `{limit}` 个。
- 每个候选点必须包含费用、过夜、停车、厕所、水源、信息日期、来源链接。
- 来源没提到的字段必须写未核验。
- 禁止把搜索页、地图入口页、政策汇总页当事实来源。
- 禁止编造坐标、设施、开放状态。
- 对安全、合法、过夜、明火只陈述事实，不做最终保证。

对数量的影响：

- “最近、可追溯、地点强相关”会让模型少选来源。
- “每个候选点必须字段齐全”会让模型倾向于少列点。
- `{limit}` 仍会影响模型重点列出的数量，但不再写成“以内”的强限制。
- “不要编造”会减少看似丰富但无证据的候选。

## 五、第一段 Ark Responses API 参数

代码位置：`backend/app/services/ai_service.py` 的 `call_seed_web_answer`

当前请求参数：

```json
{
  "model": "来自 .env 的 ARK_MODEL",
  "input": [
    {
      "role": "user",
      "content": [
        {
          "type": "input_text",
          "text": "上面的联网回答提示词"
        }
      ]
    }
  ],
  "tools": [
    {
      "type": "web_search"
    }
  ],
  "stream": false
}
```

这里的约束：

- 使用 Seed 模型。
- 只启用 Ark `web_search`。
- 不启用 Tavily。
- 不启用自建爬虫。
- 不使用流式输出，必须等完整回答返回。

对体验的影响：

- 首搜速度慢，因为要等待联网搜索和完整回答。
- 不能像 Seed 网页一样边搜边显示。
- 可追溯来源数量取决于 Ark Web Search 返回结果。

## 六、第二段 Seed 结构化抽取提示词

代码位置：`backend/app/services/ai_service.py` 的 `call_seed_structured`

当前提示词核心结构：

```json
{
  "role": "system",
  "task": "把联网回答抽取成地图产品可用JSON。只能依据answer_text和sources抽取，不得编造。",
  "rules": [
    "spots只放具体地名、营地名、村庄/公园/景区内明确点位，不能放文章标题、城市名、搜索词或泛化描述。",
    "source_ids必须来自sources中的id，不能自造。",
    "lat/lon只有在文本或来源明确给出坐标时填写；没有坐标就留空，后端会地理编码。",
    "如果只有地点线索但定位不够明确，仍放入spots，后端会决定是否入图或转为unmapped_candidates。",
    "未核验字段用unknown或来源未提到，不要推断。"
  ],
  "input": {
    "query": "用户问题",
    "max_spots": "limit",
    "answer_text": "第一段Seed联网回答",
    "sources": "Ark Web Search返回的来源列表"
  },
  "output_schema": {
    "spots": [
      {
        "name": "具体点位名",
        "province": "省份或unknown",
        "city": "城市或unknown",
        "district": "区县或unknown",
        "address_hint": "地址线索或unknown",
        "lat": "明确坐标数字，否则null",
        "lon": "明确坐标数字，否则null",
        "type": "商业营地/景区露营区/野外露营点/停车露营点/公园草坪/未知",
        "location_confidence": "high/medium/low/pending",
        "mentioned_facilities": ["停车", "厕所", "水源"],
        "mentioned_scenarios": ["自驾", "露营", "过夜"],
        "price_clues": ["免费/收费/未知"],
        "positive_summary": "来源事实摘要，不超过90字",
        "negative_summary": "风险或信息缺口，不超过90字",
        "risk_tags": ["信息不足"],
        "ai_rating": 3.8,
        "source_ids": ["s001"],
        "reason_for_exclusion": ""
      }
    ],
    "unmapped_candidates": [
      {
        "name": "有来源但无法明确定位的候选线索",
        "city": "城市或unknown",
        "district": "区县或unknown",
        "address_hint": "地址线索或unknown",
        "reason": "无法入图原因",
        "source_ids": ["s001"]
      }
    ],
    "query_summary": "不超过120字"
  }
}
```

这里对 AI 的主要约束：

- 只能依据第一段回答和来源列表抽取。
- 不能补充模型自己知道的地点。
- 不能放文章标题、城市名、搜索词、泛化描述。
- `source_ids` 必须来自真实来源。
- 坐标必须是来源明确给出，否则留空。
- 未核验字段不能推断。
- 结构化输出上限仍是 `limit`。

对数量的影响：

- 如果第一段回答只列了 4 个点，第二段不能凭空扩成 20 个。
- 如果来源引用没有覆盖某个地点，点位会在后端被丢弃。
- 如果地点名太泛，后端会过滤。

## 七、后端来源 ID 约束

代码位置：`backend/app/services/ai_service.py` 的 `normalize_candidates`

当前规则：

- 点位必须带 `source_ids`。
- `source_ids` 必须能在 Ark 返回的来源列表中找到。
- 没有来源 ID 的点位不进入地图，也不进入未入图线索。

影响：

- 可以防止 AI 编出无来源点位。
- 但也会减少点位数量。
- 如果 Seed 回答文本里提到地点，但 Ark citation 没有结构化成来源 ID，该地点可能被丢弃。

## 九、地理编码与入图约束

代码位置：`backend/app/services/ai_service.py` 的 `normalize_candidates`

当前入图规则：

```text
如果 AI 给了 lat/lon：
  使用 AI/来源坐标，location_confidence = high

如果没有 lat/lon：
  先用高德地理编码
  成功则 location_confidence = medium

如果没有坐标，也无法地理编码：
  转入 unmapped_candidates

如果坐标超出经纬度合法范围：
  转入 unmapped_candidates

如果坐标明显偏离查询地点：
  转入 unmapped_candidates

如果只能定位到城市级别：
  转入 unmapped_candidates
```

影响：

- 地图上只展示高/中置信定位点。
- 模糊地点不会用城市中心伪坐标凑数。
- “文章提到一个区域附近可露营”但没有具体点名时，不会入图。

## 十、坐标偏离过滤

代码位置：`intel_server.py` 的 `coordinate_near_expected_location`

当前规则：

```text
从用户 query / 点名 / 地址中识别已知地点。
如果识别到地点，例如杭州、安吉、富阳、台州等：
  要求地理编码坐标距离该地点中心不超过 160km。
超过则判定偏离，转入 unmapped_candidates。
```

影响：

- 可以避免“安吉”搜出外省同名地点。
- 但如果用户搜的是“浙江省”或大范围路线，160km 可能偏紧。

## 十三、当前链路中的“质量优先”约束汇总

以下规则共同导致点位数量偏少：

```text
实时 AI 默认 limit=12
只用 Seed web_search
不使用 Tavily 兜底
使用 OSM/公开资料/审核后的 AI 候选作为 POI 底库
不使用高德 POI 搜索批量兜底
每个点必须有来源 ID
不能编造地点
不能编造设施
不能编造坐标
不能用文章标题当点位
不能用城市中心伪坐标
地理编码结果偏离就不入图
时间筛选启用后排除日期未知点
```

## 十四、如果要提高点位数量，可修改的方向

### 方案 A：轻量修改，继续走 Seed Web Search

适合短期 P0.3。

可改：

```text
前端 limit=6 改成 limit=12 或 limit=20。
第一段提示词从“请尽量列出 {limit} 个以内”改成“请尽可能多列出候选线索，至少优先列出 {limit} 个”。
第二段结构化抽取把 max_spots 提高到 20。
未入图线索在前端更明显展示。
```

风险：

- 首搜更慢。
- Seed 可能仍只返回少量引用来源。
- 数量提升有限。

### 方案 B：地图 POI 候选池 + AI 核验

更接近窝友自驾。

链路：

```text
用户输入城市/路线
↓
高德 POI / OSM / 历史缓存 搜索大量候选点
↓
AI 对候选点批量联网核验
↓
地图展示大量点位
↓
详情页标记：已核验 / 待核验 / 来源不足
```

优点：

- 地图上天然有更多点。
- 用户体验更接近窝友自驾。
- AI 负责分析、补标签、总结来源，而不是独自承担“生成全部点位”。

风险：

- 需要接高德 POI 搜索或维护本地候选库。
- POI 点位本身不等于可露营，需要 AI/来源二次核验。

### 方案 C：本地缓存沉淀为产品资产

适合中期。

链路：

```text
每次用户搜索后，把候选点、来源、更新时间、坐标、AI标签保存到本地/数据库。
下一位用户搜索同一区域时，先展示历史候选点。
后台或用户触发时再更新信源。
```

优点：

- 越用点位越多。
- 可逐步形成“AI版窝友自驾”的资产。

风险：

- 需要数据结构、去重、过期策略和审核机制。

## 十五、建议下一版产品策略

如果产品目标是“窝友自驾的 AI 版本”，建议把 P0.3 调整为：

```text
地图点位数量优先来自候选池。
AI 联网搜索负责核验和解释。
点位不再只有“入图/不入图”二分，而是分层展示：
  1. 已核验：有具体坐标 + 至少1个近期来源
  2. 可疑但可看：有坐标 + 来源不足
  3. 线索：有来源 + 坐标不足
  4. 排除：明确禁停/关闭/风险高
```

这样既能解决数量问题，又不牺牲事实可信度。
